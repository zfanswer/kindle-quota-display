# 离线省电与自动恢复方案

状态：**2026-10-10已获准并实现，Mac服务与Kindle增量部署完成；已记录一轮自动刷新；专项早醒/换网与夜间功耗待测**。本版以统一线性规则替代按作息分段的提案；当前源码契约见[Spec](../spec.md)和[技术设计](../design.md)。

## 1. 核心规则

统一采用连续失败计数，白天、夜间、上午及外出均使用同一规则。

| 本轮结果 | 连续失败计数 | 下一次RTC等待 |
| --- | --- | --- |
| 成功绘制并提交有效PNG | 清零 | 3分钟 |
| 第1次连续失败 | 1 | 3分钟 |
| 第2次连续失败 | 2 | 6分钟 |
| 第3次连续失败 | 3 | 9分钟 |
| 第4次连续失败 | 4 | 12分钟 |
| 第5次及更多连续失败 | 保持5 | 15分钟 |

```text
成功：failure_streak = 0；next_delay = 180
失败：failure_streak = min(failure_streak + 1, 5)
      next_delay = failure_streak × 180
```

这里“第1次失败后”等3分钟，第2次失败后才增加到6分钟。等待从当轮工作结束后计算，实际两次探测之间还包含联网/下载开销。恢复一次成功后，下一次失败重新从3分钟起步，不沿用旧的15分钟退避。

failure按一次完整刷新轮次计数，不按每个HTTP请求计数：缓存IP探测失败但随后主机名成功并完成绘图时，仍是成功轮次。只有本轮未完成有效PNG绘图才增加一次连续失败计数。

首版直接固定180秒步长、900秒上限，正常在线仍使用现有INTERVAL=180；不增加作息、时区、夜间或上午恢复配置。失败计数位于/tmp，重启或重新开启任务后清零；重新启动不自动扫描。

## 2. 自动与手动发现

**已确认的约束**：自动探测只使用最近成功缓存、配置IP和配置主机名，去除重复候选。三者均失败后立即结束本轮，不扫描子网，不在其他失败分支偷偷触发扫描。继续严格核验healthz协议和SERVER_ID。

完整子网扫描仅由用户点击“重找额度服务器”触发。更换网络，或同网DHCP换IP且主机名不能解析时，都接受手动重找；主机名仍可访问时可以自动恢复并更新缓存。不能把“同一Wi-Fi”视为“IP一定没变”。

`find-server.sh`增加明确的known-only调用方式，自动worker、bootstrap及普通刷新统一使用；默认调用也限制为已知地址。`--force`及ENABLE_SCAN仅允许显式手动完整扫描，保留私有/22至/30、身份校验和16并发限制。

手动重找必须跳过退避并尽快刷新：有活动worker时由该worker接收固定请求并执行，避免另起进程同时控制Wi-Fi/RTC、以及当前“找到地址后refresh被运行锁拒绝”的问题。只通知核验属于本项目的进程；停止优先、结果对应本次请求、重复点击合并。没有worker时在独占锁下做单次发现与刷新，不擅自启动自动任务。遗留锁不能盲目删除。

## 3. 对实际使用的影响

| 场景 | 新行为与取舍 |
| --- | --- |
| Mac一直在线 | 保持工作后3分钟RTC等待 |
| 19:30离开，次日08:30返回 | 长时间离线后维持15分钟短探测；不会在早上自动缩短间隔。已知地址有效时，自动恢复可能额外等待最多15分钟，再加联网开销 |
| 白天离开公司两小时后返回 | 同样已退避到15分钟，自动恢复也可能额外等待最多15分钟，再加联网开销 |
| 返回后希望立即更新 | 主动点“重找额度服务器”，跳过等待并尝试立即发现/刷新 |
| 网络或地址变化且已知候选均失效 | 保留旧画面并持续轻量退避，等待手动重找 |

这是用户选择简化逻辑后的明确取舍：取消上午3分钟、白天5分钟的特殊恢复目标，统一接受最多15分钟的额外RTC等待。自动恢复以服务已运行、局域网可互访且至少一个已知候选有效为前提；不承诺无线故障、AP隔离或无可用地址时的时限。

相同假设下可计算探测数量，但不能由次数预测电池下降比例。Mac离线与RTC早醒是独立路径，没有证据把一晚50%的电量下降全部归因于任一分支。

## 4. 保留的必要省电约束

### 网络与图片

- 普通自动轮次共用30秒网络总预算，覆盖无线就绪、解析/健康检查、PNG下载及允许发送的遥测；各操作timeout不能超过剩余预算。FBInk和收尾另外设置短超时，不把30秒误报为整机清醒时间硬上限。
- 在预算内允许短间隔就绪/已知地址重试，改善固定等8秒的误判。IPv4存在不代表服务器可达；没有可用IPv4也不扫描子网。curl/wget均受外层预算约束。
- 手动扫描保留90秒扫描上限，含联网的手动网络总窗口为120秒。超时或停止回收本次拥有的子进程，再释放工作目录和锁。
- 每轮失败保留最近成功PNG及其原数据时间，不重画旧图、不刷新成功时间。无有效缓存时沿用固定卡片式占位图。
- 服务器已知不可达时跳过HTTP诊断POST；仅在本地记录少量固定汇总，保持日志轮换，不逐IP记录。恢复连接后上报当前事件，不补造缺失的历史事件，不扩展现有HTTP白名单。

### RTC与停止

- `arm_rtc(delay)`接收显式等待时长；普通计划为180–900秒，提前返回后的剩余正数时长也可重新设置，不能设置零秒alarm。正常INTERVAL不被改写成退避值。
- 所有退避均关闭无线并通过RTC请求系统挂起，不能改成开着无线sleep 900。
- 记录本轮计划截止时间；提前返回时先判断停止/手动请求及计划是否到期，再决定是否联网。单次早醒不结束任务；必要的短本地交互后，用剩余计划重新RTC挂起，不重置完整等待、不增加失败计数。
- 保留有限的连续立即返回保护，避免反复挂起/立即返回的快速循环：规定60秒内3次挂起仅持续0–2秒且无待办请求，或明确挂起失败，按已有suspend_failed错误路径退出并归还原生电源管理。此异常保护可能恢复原生待机页，是已批准的故障保护例外。
- 只操作本次拥有的alarm，保留其他进程的alarm；停止可中断探测/等待，完成锁、PID、子进程及原状态清理。不为停止遥测额外开无线。
- 工作预算和RTC经过时间使用经验证的单调/含挂起时间计时，避免墙钟校时延长预算。这里只保证时间测量正确，不再引入作息时钟状态。

无有效PNG的网络/下载/解码失败增加连续失败计数；无额度fallback的有效PNG仍算成功。手动取消和停止不算网络失败；HTTP 500或坏PNG不触发全网扫描。

## 6. 实施与验收

1. 先在现有脚本测试中固定失败序列及计时，写出能捕捉当前“每轮失败仍扫描、固定180秒等待”的回归。
2. 改known-only与有界网络访问，再接入线性退避和RTC等待；同步手动重找和bootstrap，不能部署一半实现。
3. 验证停止/早醒/锁/PID/子进程和缓存行为，执行正常离线检查及干净源码复验。
4. 审阅通过并获部署授权后，停止任务、USB备份、按文件清单更新并hash核验，安全推出后重新启动。更新保留个人配置；回滚恢复配套旧脚本，不清理其他Kindle文件。
5. 再做服务在线/离线、同网恢复、手动换网、夜间电量和视觉验收。

| 核心验收 | 必须满足 |
| --- | --- |
| 连续失败1、2、3、4、5、6次 | RTC等待为180、360、540、720、900、900秒 |
| 失败到上限后成功，再次失败 | 成功清零并等180秒；随后第1次失败仍等180秒 |
| 任意时间/跨午夜/长时间离线 | 同一失败序列得到相同结果，无作息分支、无计数溢出 |
| 自动已知候选均不可达 | 不产生子网扫描；保留好缓存；预算后关无线并RTC等待 |
| 无IPv4、慢解析、HTTP 500、坏PNG、挂住请求 | 不自动扫描或无限等待；回收拥有的子进程 |
| 15分钟等待中手动重找 | 跳过退避，由单一执行者扫描并立即尝试刷新；成功后清零 |
| 同网DHCP换IP且主机名失效 | 自动路径继续轻量退避；只在手动请求后扫描 |
| 提前返回、停止、RTC busy、校时、遗留锁 | 不把剩余等待变为长时间普通sleep，不覆盖他人alarm或误发信号，正确清理 |
| 离线启动及无/坏缓存 | 设备自检通过后可省电等待，正确使用固定占位，无自动扫描 |
| 诊断及更新包 | 离线不POST、日志有界，HTTP原白名单有效，设备个人配置保留 |

电量对比固定前光、相近起始电量和观察时长，分别记录清醒/无线开启时间、实际RTC等待、探测及扫描次数。模拟跨13小时不等于真实续航；在实测前不承诺具体电量改善。

参考：[Linux系统休眠说明](https://docs.kernel.org/admin-guide/pm/sleep-states.html)、[/proc/uptime计时说明](https://man7.org/linux/man-pages/man5/proc_uptime.5.html)。PW3的实际计时和挂起能力仍须验证。

用户已批准统一退避及配套实现；当前离线验证不能替代真实夜间功耗和设备验收。安装包采用--update保留设备配置/地址缓存，不重新添加临时恢复入口；源码修改本身不更新设备。
